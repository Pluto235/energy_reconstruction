# 一月观测 Nhit：PINC 顺序提取方案实测

2026-10-15，在隔离目录对三个完整文件做同节点成对测试。原有全月任务持续运行，未修改生产代码、任务、验收记录或正式 friend。

结论：源端合计加速 **1.68 倍**；计入真实传输、ETO 对齐、标量结果生成和完整读回后，处理耗时合计加速 **1.78 倍**，由 **995.2 秒降至 558.0 秒**，节省 **43.9%**。这些时间不包含排队、进程启动和接收器轮询等待，不能直接等同于全月完成时间。

## 对照方法

- 基线：冻结当前正在使用的提取代码，重新执行全部身份键扫描、30 个共同分支核对、原电荷输出、源端完整读回、实际传输和 ETO 原电荷重算验收。
- 新方案：IHEP 仅按 `pincness < 1.1` 顺序筛选；只读取选中事件的完整 `vqsamp/vt/vidmc/nv` 与身份，计算 `sum((vqsamp >= float32(0.3)) & (abs(vt) < 30))`；使用同一 segment header 定位及身份核验逻辑取得 poolused。无其他物理筛选。
- 新方案不在 IHEP 与 ETO 请求键匹配，且不保存或传输 vqsamp。ETO 检查键重复、缺失、多余事件，按原观测输入对齐，逐事件比较新旧键、nv、Nhit、poolused 和 ihep_entry。随后生成含 input_entry 的标量测试 friend，完整读回并保存摘要。
- 新方案不做 ETO 原电荷独立重算，不核对全部 30 个共同分支；其验收工作与基线不同。这里测的是用户提出的工作流整体变化，不把收益单独归因于移动四元键匹配。
- 一个 HTCondor worker，1 CPU / 4 GB，同一节点 bws0876，依次执行三组。Jan01/Jan31 为基线先执行，Jan16 为新方案先执行。ROOT 加载和编译约 13.2 秒，单独记录。ROOT 缓存 8 MiB 用于 PINC 扫描、32 MiB 用于选中事件命中读取，复用恢复流程中已测量的方法。
- Slurm 66148 负责提取控制/传输/对照验收；依赖其成功完成的 Slurm 66150 生成并完整读回对齐后的标量测试结果。两者均 COMPLETED、退出码 0。HTCondor 为 3739428，无重复提交。

## 大小与剩余瓶颈

| 完整文件 | 基线 friend / MB | 新方案传输文件 / MB | ETO 对齐后标量 friend / MB |
|---|---:|---:|---:|
| Esg20220101_00.root | 71.906 | 2.713 | 3.396 |
| Esg20220116_00.root | 46.204 | 1.445 | 1.798 |
| Esg20220131_00.root | 29.966 | 0.865 | 1.070 |

合计 **148.08 MB → 6.26 MB**，缩小 **23.6 倍**，减少 **95.77%**。按样本压缩后每事件大小估算，6928 万事件约 **0.75 GB（0.69 GiB）**；实际月度分布和元数据开销尚未测量。

三文件新方案的命中读取/计算/写入分别为 146.1、138.2、61.4 秒；segment header 为 40.2、57.7、31.6 秒。PINC 扫描分别为 25.2、18.1、8.5 秒。ROOT 客户端命中阶段记录读取约 9.02、6.61、5.02 GB：选中约 3% 的事件，不等于只读约 3% 的 ROOT 压缩数据块。以上字节/调用数是客户端 ROOT 计数，不能作为服务端实际 RPC 数。

各文件加速不一致，新方案并非总能加速数倍。排队与启动、header 远程打开、ROOT 数据块读取仍存在；没有测试多 worker 吞吐，也未分离每一项代码改动的贡献。
